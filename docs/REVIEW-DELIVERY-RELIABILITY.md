## 已确认的性能原因

前期只读诊断表明，“PostgreSQL 数据变多”不是主要解释：

- 审核 JSON 状态约 7.1 MB，1463 条审核、2432 条投递历史。原进度更新反复重写整个状态文件，并触发多个阶段重新读取。
- 媒体校验曾为每张图片重复建立历史路径与任务 ID 映射。66 次校验中，约 3.52 秒用于反复构建映射；复用映射后同一组校验约 99 毫秒。
- 单次 22 张、约 6.34 MiB 的慢投递达到约 50 秒，同时出现重复阶段查询和大量历史媒体补偿警告。
- 原写入门禁为每次请求读取旧根相关的历史下载任务和通知详情；实际非终态任务检查只需少量活动记录。

这些数字用于说明诊断依据，不能把历史最慢值当作每次请求的基准。

## 实现

### 状态保存与单写入者

`StateStore` 将整个事务串行执行：隔离副本 → 校验 → 原子写入并 fsync → 发布内存状态和事件。写入失败不会先更新内存；损坏或不支持的状态文件拒绝启动，不会重置为空库。

热路径采用按区读取、按区更新与审核索引；历史任务 ID 映射按身份变化失效。仅实际受影响的阶段收到审核状态事件。纯进度保存在内存，经单独 SSE 通道最多每秒推送一次，不触发全库保存或全阶段刷新。

同一真实 APP_DATA_DIR 使用内核持有的本机回环端口预留作为独占写入锁。进程退出或崩溃后由操作系统释放，不按超时抢占仍存活的进程。端口冲突会拒绝启动。该锁只协调支持本协议的新版本；发布时仍须按原发布门禁停止旧实例。

首次出现操作或交付检查点时，状态格式升为 `1.1`，并保留 `db.before-review-operations-v1.json`。它是升级前副本，不是发生后续投递后的可直接回滚数据。

### 接收、版本校验与进度

审核、批量投递和重试进入持久化操作队列。浏览器保存 Idempotency-Key；相同编号、相同内容返回原操作，相同编号、不同内容返回 409。同一任务的活动操作互斥，事务内再次检查，避免检查和保存之间的竞争。

请求冻结任务、媒体元数据、目录配置、参数模板、产品身份、变体和平台投递编号。审核版本及待投递版本不匹配时拒绝接收。任务排队后参数不能被另一个请求修改；来源文件在接收后变化时停止本次交付。

带 `Prefer: respond-async` 的请求仅在操作落盘后返回 202 和操作地址。旧客户端继续等待同一执行器，并保留原完成响应格式。202 表示已接收，不表示拷贝完成。

- 活动队列上限为 200 个待处理项。
- 操作按接收顺序调度；普通投递与两个共享媒体平台共用最多 2 个文件处理槽。
- 相同目标目录命名空间和相同共享归档的提交串行处理。
- 页面刷新后向服务器重新获取操作状态；SSE 断开时每 2 秒轮询。
- 状态文件不可写时暂停派发，不连续空转重试；恢复磁盘后用“恢复处理”继续原操作。
- 已验证为提交前的瞬时 EBUSY、EPERM、EAGAIN 最多按 1、3、10 秒重试；原子目录重命名保留原有占用重试。

### 普通监听目录交付

1. 验证来源与冻结元数据，持久化固定 submissionId 和暂存、目标、归档路径。
2. 流式复制媒体，记录真实字节进度，检查来源变化、目标大小与 SHA-256。
3. 保持既有选图顺序、参数文件名、task-context、selection-manifest、handoff 和 READY 契约。
4. 在公开监听目录前，先完成归档暂存包；校验所有文件并刷新文件数据。
5. 保存 COMMIT_INTENT，再同卷原子重命名目标目录。
6. 保存 TARGET_COMMITTED 回执，完成归档，原子更新业务记录。

下游在目标重命名后立即取走目录，也不会阻止已有归档暂存包完成。跨目标共享归档保留每个目标的冻结参数文件，并核对媒体内容。来源文件不被删除。

### E004/E005 共享媒体与通知

两个平台使用独立固定 submissionId、独立检查点和结果。共享清单是可见提交点；恢复时先核对原清单中的 submissionId、顺序和哈希。已提交的平台不重复生成媒体；归档失败仅恢复归档部分。

投递记录与通知 outbox 一起保存。通知失败保留原 submissionId，并退避重试；通知采用至少一次投递，沿用下游已有的幂等登记契约。已证明属于同一清理批次、同一媒体签名及完整终态依赖的 WB 事件，不重新使已清理媒体变成新媒体。

### 崩溃恢复规则

| 可验证状态 | 动作 |
| --- | --- |
| 只有 PREPARING/VERIFIED | 使用原编号重建自己的暂存包 |
| COMMIT_INTENT，完整暂存仍在且目标不存在 | 验证后继续原子提交 |
| 目标或共享清单与冻结记录匹配 | 补回执、归档和业务状态 |
| TARGET_COMMITTED | 只完成归档及状态 |
| 暂存与目标都不见、无法证明已消费 | NEEDS_ATTENTION，保留证据和任务锁，不重新入队 |
| 多平台部分成功 | 复用已成功检查点，只处理未完成部分 |
| 参数、选图或目录与失败检查点不一致 | 拒绝复用，要求重新核对并生成新的待投递项 |

升级前处于 PACKAGING/FAILED、没有交付检查点及新协议接收记录的历史项，不会被直接当作新任务重新投递。应先核对原目标和历史结果。设置中的暂存清理也不能删除未完成检查点引用的目录。

Windows 使用文件 fsync 与同卷原子重命名；POSIX 另外刷新目录。没有在本次测试中执行物理断电测试，磁盘或控制器故障后的持久性仍受操作系统和硬件保证范围约束。

### 历史补偿

WB/OZON 历史补偿使用持久化游标、已解决身份和未解决重试记录，每轮最多 20 条，共享单并发。活动审核执行时暂停历史回放，不停止结果回写、租约处理或已有自动上品执行器。新媒体、变更后的媒体身份及待处理数据库记录继续处理。

写入门禁只查询非终态下载任务。全历史路径统计保留在只读诊断入口。
